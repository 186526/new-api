# 第三方托管搜索、网页抓取与引用契约

本报告用于判断哪些上游接口可以为 `tools-search` 与 `tools-fetch` 提供数据，以及接入前还需要取得哪些响应样本。依据仅为供应商公开文档与本仓库源码；本次没有使用凭据调用任何供应商 API，也没有验证部署中的账号权限、模型或地域可用性。

**判定标准。** 托管搜索由供应商执行查询，可输出结构化结果，也可仅输出带来源的模型回答。网页抓取要求按调用者指定的 URL 取得可交付的网页正文；模型读到网页、生成摘要、返回链接或记录打开页面的动作，都不等同于调用方收到了正文。引用是回答与来源的对应关系；纯链接列表也不能冒充有原文摘录、站点名称或发布日期的搜索结果。已登记的渠道能力见 [`pkg/toolcatalog`](../pkg/toolcatalog/catalog.go)；AdvancedCustom 还须通过下文的逐渠道、逐操作验证。按[仓库规则](../.agents/rules/websearch.md#routing-and-provider-isolation)，供应商文档可以作为接入依据，实际宣告能力前还需要重放响应样本。

## Gemini Developer API 与 Vertex AI 将抓取内容用于模型上下文

- **搜索与引用。** Gemini Developer API 的 `:generateContent` 接受 `tools:[{"google_search":{}}]`，返回候选项中的 `groundingMetadata`，包括 `webSearchQueries`、`groundingChunks[].web`（URI、标题）及通过索引关联的 `groundingSupports`。Vertex AI 的 Gemini 推理接口同样提供 Google Search grounding。两者均由模型决定是否调用搜索，返回的引用也不等于完整排名列表。[Gemini GenerateContent 搜索](https://ai.google.dev/gemini-api/docs/generate-content/google-search) · [Google Cloud 搜索](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-google-search)
- **指定 URL。** `url_context` 从提示词读取公开 URL，优先使用索引，未命中时再实时抓取。GenerateContent 返回模型文本及 `urlContextMetadata`（抓取 URL 与状态）。Interactions 的 `url_context` 返回模型文本、`url_citation` 和 `url_context_result`（URL 与状态）；同一 API 的 `google_search` 使用调用步骤与文本上的引用。上述接口未承诺向调用方返回检索到的网页正文。[Gemini URL Context](https://ai.google.dev/gemini-api/docs/url-context) · [Gemini Interactions 搜索](https://ai.google.dev/gemini-api/docs/google-search) · [Google Cloud URL Context](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/url-context)
- **鉴权与待验证。** 现有 [Gemini 适配器](../relay/channel/gemini/adaptor.go#L155-L167) 使用 `x-goog-api-key`；[Vertex 适配器](../relay/channel/vertex/adaptor.go#L132-L215) 使用项目凭据取得 OAuth Bearer 令牌，或把 API key 放入查询参数（无项目 ID 时使用 Express 路径）。需用对应项目、地域、版本和模型验证实际搜索结果是否含来源、引用 URI 是否重定向、指定 URL 的成功与失败状态；不能凭成功状态启用正文抓取。

## 智谱提供独立搜索与网页正文接口

- **搜索与引用。** 中国站 `POST https://open.bigmodel.cn/api/paas/v4/web_search` 接受 `search_query`、`search_engine`（如 `search_std` 或 `search_pro`）和 `search_intent`（直接检索时为 `false`）；`search_result[]` 包含 `title`、`link`、`content`（摘要）、`media`、`refer` 和 `publish_date`。聊天内搜索是另一条路径，启用工具后可输出答案引用及 `web_search` 来源数据。[智谱搜索 API](https://docs.bigmodel.cn/api-reference/工具-api/网络搜索) · [智谱联网搜索指南](https://docs.bigmodel.cn/cn/guide/tools/web-search)
- **指定 URL。** `POST https://open.bigmodel.cn/api/paas/v4/reader` 接受 `url` 和可选 `return_format`（默认 `markdown`）；正文在 `reader_result.content`，同级还有 `url`、`title`、`description`。链接和标题是页面属性，无需从生成答案中解析。[智谱网页阅读 API](https://docs.bigmodel.cn/api-reference/工具-api/网页阅读)
- **鉴权与待验证。** 中国站 REST 使用 Bearer API key。国际站的同类 API 以 `https://api.z.ai/api` 为基址，搜索引擎枚举使用 `search-prime`；勿混用主机、引擎和账号凭据。Coding Plan 另有[搜索 MCP](https://docs.bigmodel.cn/cn/coding-plan/mcp/search-mcp-server)和[网页读取 MCP](https://docs.bigmodel.cn/cn/coding-plan/mcp/reader-mcp-server)，产品说明不能证明订阅凭据也适用于普通 REST。当前 [ZhipuV4 渠道](../relay/channel/zhipu_4v/adaptor.go#L75-L95) 的聊天鉴权同样使用 Bearer；需分别验证该账号的搜索引擎权限、Reader 权限、配额、空结果和错误返回。[国际站搜索](https://docs.z.ai/api-reference/tools/web-search) · [国际站 Reader](https://docs.z.ai/api-reference/tools/web-reader)

## Claude Messages 可返回抓取正文，AWS 产品需要分开处理

- **Claude API 搜索与引用。** `POST /v1/messages` 使用 `x-api-key` 和 `anthropic-version`，在 `tools` 声明 `web_search_20250305` 等版本。`server_tool_use` 记录调用，`web_search_tool_result` 返回 URL、标题、`page_age` 与加密内容；正文块内的 `web_search_result_location` 引用可含 `cited_text`。`page_age` 是站点更新线索，不能直接当作发布日期。[Claude 搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)
- **Claude API 指定 URL。** 在用户消息提供 URL，并声明 `web_fetch_20250910` 或适用版本。`web_fetch_tool_result.content` 中的 `web_fetch_result` 含 URL 和 document；网页文本在 `content.source.data`，PDF 则为 base64。设置 `citations.enabled` 可启用文档引用，默认关闭；HTTP 200 也可能携带工具级错误。需要验证账号工具开关、模型与版本，取得工具实际执行、明文结果、不可访问 URL 及工具错误样本；不能以回答文本替代工具结果块。[Claude 网页抓取](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)
- **Claude Platform on AWS。** Anthropic 的工具文档明确列出搜索和抓取；该服务使用 AWS IAM SigV4 或工作区密钥，需验证工作区、地域和模型，不能将 Claude API key 或 Bedrock 凭据用法直接套用。[Claude Platform on AWS](https://platform.claude.com/docs/en/build-with-claude/claude-platform-on-aws) · [AWS 平台鉴权](https://platform.claude.com/docs/en/build-with-claude/authentication-aws)
- **Amazon Bedrock。** 本仓库 [AWS 渠道](../relay/channel/aws/relay-aws.go#L130-L165) 走 Bedrock Runtime 的 `InvokeModel` 系列。AWS 公开的托管 Web Search 是另一接口：`bedrock-mantle` 的 `/openai/v1/responses`、支持的 OpenAI GPT 模型及地域、Bedrock Bearer API key 与 IAM 搜索/抓取权限。它支持模型内部的 Search（标题、URL、摘要）和 Fetch（缓存正文；实时抓取还需 `bedrock-websearch:ExternalWebAccess` 和 `external_web_access:true`），对调用方公开 `url_citation`，且该引用不能证明抓取成功。该文档明确排除 `bedrock-runtime` 的 Responses 路径，也未将此能力授予仓库所用的 Bedrock Claude `InvokeModel`。在为现有 AWS 渠道登记能力前，需取得其实际上游接口、模型、地域、权限及独立响应证据。[AWS Web Search](https://docs.aws.amazon.com/bedrock/latest/userguide/web-search.html) · [Bedrock Claude 工具](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages-tool-use.html)

## OpenAI、Azure OpenAI 与 xAI 返回搜索来源，未确立正文抓取契约

- **OpenAI。** `POST https://api.openai.com/v1/responses` 使用 Bearer API key，传入 `model`、`input`、`tools:[{"type":"web_search"}]`。有实际搜索时检查 `output[]` 的 `web_search_call`；`include:["web_search_call.action.sources"]` 返回模型查阅的 URL，回答文本中的 `url_citation` 给出 URL、标题及字符范围。推理模型可以执行 `open_page` 和 `find_in_page`，但文档未承诺以指定 URL 返回可交付的网页正文。Chat Completions 仅有专用搜索模型路径，不可用来推断普通模型可搜。需用对应模型和项目 key 验证工具执行、来源字段及其完整度。[OpenAI Web Search](https://developers.openai.com/api/docs/guides/tools-web-search)
- **Azure OpenAI。** 对资源的 `/openai/v1/responses` 使用 `api-key` 或 Microsoft Entra Bearer（文档示例 scope 为 `https://ai.azure.com/.default`）；`model` 指部署名。`web_search` 返回调用记录、回答和 `url_citation`；可按需包含 `action.sources`，推理模型还支持请求 `web_search_call.results` 以取得搜索摘要。微软明确说明 `external_web_access` 始终按 `false` 处理，且 `open_page`、`find_in_page` 的结果不会通过该字段交付。需验证订阅开关、部署及实际响应；[仓库 Azure 适配器](../relay/channel/openai/adaptor.go#L127-L195) 使用 `api-key`，并有不同的 Responses 路径分支，不能假设每种配置都走 v1。[Microsoft Web Search](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/web-search)
- **xAI。** `POST https://api.x.ai/v1/responses` 使用 xAI Bearer key，给支持的 Grok 模型传 `tools:[{"type":"web_search"}]`；服务可搜索并浏览网页。Responses 默认可输出 `[[N]](url)` 与 `output_text.annotations[]` 的 `url_citation`，该注解的 `title` 对文本引用是编号标签，不能当作网页标题；xAI SDK 另有全部来源 URL 的 `response.citations`。公开文档未说明可直接按指定 URL 返回完整网页正文。需验证具体模型、调用记录、来源字段与 URL 浏览行为。[xAI 搜索](https://docs.x.ai/developers/tools/web-search) · [xAI 引用](https://docs.x.ai/developers/tools/citations)

## Ali 的搜索来源与网页提取字段因协议而异

- **搜索与引用。** Model Studio 使用对应地域和工作区的 DashScope Bearer key。原生 DashScope 在 `parameters` 下传 `enable_search:true` 和 `search_options.enable_source:true`，返回 `output.search_info.search_results[]` 的索引、标题和 URL；OpenAI 兼容 Chat Completions 的 `enable_search:true` 不返回结构化来源。兼容 Responses 在 `/compatible-mode/v1/responses` 中声明 `web_search`，从 `output[]` 的 `web_search_call.action.sources` 读取链接，不支持 DashScope 的 `enable_source`、`enable_citation`、`citation_format`。[Model Studio 搜索](https://www.alibabacloud.com/help/en/model-studio/web-search)
- **指定 URL。** Responses 使用 `web_extractor`、`web_search` 与 `enable_thinking:true`；文档示例可从流式 `web_extractor_call` 读取 `goal` 和 `output`。Anthropic 兼容接口使用工作区的 `/apps/anthropic` 基址，要求同时启用 `web_fetch` 与 `web_search`，直调按文档把 `x-anthropic-billing-header: cc_entrypoint=cli;` 作为 `system` 内容，返回 `web_fetch_tool_result`；不能用 Responses 或其他供应商的字段猜测正文形状。[Model Studio 网页提取](https://www.alibabacloud.com/help/en/model-studio/web-extractor)
- **待验证。** [Ali 适配器](../relay/channel/ali/adaptor.go#L102-L123) 有 Responses 路径和 Bearer 鉴权。须以准备接入的区域、工作区和模型验证搜索来源形状，并检查网页提取结果是否包含与所请求 URL 对应的可交付正文，以及截断、重定向和失败如何表示。网页提取文档本身没有保证结果和独立正文接口等价。

## BaiduV2 有独立搜索契约，尚未确认同一产品能按 URL 交付正文

- **搜索与引用。** `POST https://qianfan.baidubce.com/v2/ai_search/web_search` 使用千帆 Bearer API key，传入 `messages:[{"role":"user","content":"查询"}]`；文档示例使用 `search_source:"baidu_search_v2"`。`references[]` 返回 `id`、`title`、`url` 和可选 `snippet`、`content`、`website`、`date`；`content` 是相关片段，文档注明当前与摘要相同。`/v2/ai_search/chat/completions` 是生成回答加引用的单独接口，可控制 `enable_corner_markers`。部分 ERNIE 模型的常规 `/v2/chat/completions` 另有 `web_search.enable`、`enable_trace`、`enable_citation`，返回 `search_results` 和可选正文角标。[百度搜索](https://cloud.baidu.com/doc/qianfan-api/s/Wmbq4z7e5) · [智能搜索生成](https://cloud.baidu.com/doc/qianfan-api/s/Tmwbk72ho) · [模型联网搜索](https://cloud.baidu.com/doc/qianfan-docs/s/Wm8r4sw29)
- **指定 URL 与待验证。** 上述官方 API 均未定义输入指定 URL 并返回正文的契约。千帆社区的网页解析插件不能据此视为 BaiduV2 API。现有 [BaiduV2 适配器](../relay/channel/baidu_v2/adaptor.go#L45-L75) 使用 `/v2/chat/completions` 等推理路径与 Bearer；需验证同一 key 对专用搜索接口的授权、版本、配额和业务错误（文档列有 HTTP 200 内的服务错误）。如要支持 Fetch，需先确认独立服务的官方契约和凭据，再获取正文样本。[千帆社区插件页](https://qianfan.cloud.baidu.com/qianfandev/plugin/71)

## AdvancedCustom 按操作配置并验证 Exa 兼容端点

- **Web 配置。** 在「渠道 → 编辑渠道 → 连接与模型 → 搜索与抓取 → 自定义工具端点」中，先保存 AdvancedCustom 渠道及 API 地址，再分别保存 Search 和 Fetch 的路径与密钥。路径会附加到已保存的 API 地址；直连 Exa 时可使用 `https://api.exa.ai`，路径分别为 `/search` 和 `/contents`。编辑已有配置时，留空密钥会保留该操作的旧密钥。点击「验证」才会向已保存的端点发出样例请求。三项管理权限分别为查看 `ChannelRead`、保存或移除 `ChannelSensitiveWrite`、验证 `ChannelWrite`。接口不返回密钥或验证凭条。[渠道编辑](../web/src/features/channels/components/drawers/channel-mutate-drawer.tsx#L2344) · [管理路由](../router/channel-router.go#L52-L54)
- **独立鉴权和运行资格。** 当前只支持 `exa-v1`。Search 和 Fetch 各自加密保存密钥，并以 `x-api-key` 发出对应操作的请求；不借用普通渠道密钥、通用鉴权配置或全局 Exa Key。验证结果绑定渠道、操作、已保存的 API 地址、协议、路径和凭据版本，改动任一项须重新验证。旧 `websearch_provider=exa` 不使 AdvancedCustom 获得资格。验证通过后仍须满足相应 `tools-search` 或 `tools-fetch` 的渠道能力、分组和选渠约束。[配置与验证绑定](../service/websearch/abstract/custom_tools.go) · [选渠资格](../service/websearch/abstract/eligibility.go)
- **验证和转发限制。** 两者共用独立 HTTP 客户端，只直连通过地址检查的公网 HTTPS 443，连接到已经检查过的 DNS 解析地址，不走环境代理、不跟随重定向、不共享响应缓存。请求限时 10 秒，响应头上限 32 KiB，成功响应体最多 1 MiB，只接受未压缩的正文。Search 的固定样例需返回至少一条可解析的结构化 URL；常规 Search 允许空结果。Fetch 的样例需返回属于 `https://example.com/` 的非空正文，普通请求同样按指定目标匹配正文。验证失败不会用生成回答、引用或其他页面正文补齐。[出站和响应检查](../service/websearch/request/custom_tools.go)
- **验收证据。** 本地合成用例覆盖独立请求头、验证结果绑定、全局凭据隔离、出站地址判定、响应大小和目标正文匹配；前端用例覆盖单独保存、主动验证及冲突回读。未以真实账号验证实际端点兼容性、权限、额度或生产转发，不据此宣称所有 AdvancedCustom 渠道可用。[后端传输用例](../service/websearch/request/custom_tools_test.go) · [资格用例](../service/websearch/abstract/custom_tools_test.go) · [前端用例](../web/src/features/channels/components/__tests__/custom-tools-dialog.test.tsx)

## 响应解析须区分外层完成状态、工具结果和正文

- **Gemini Developer API / Vertex AI。** GenerateContent 按 `candidates[]` 分开处理：`groundingMetadata.groundingChunks[].web.{uri,title}` 提供来源；`groundingSupports[].groundingChunkIndices` 指向同一候选项的原始 chunks 数组，应先解析索引，再过滤或去重。`segment.partIndex` 指向 `content.parts[]`；`startIndex` 和 `endIndex` 是该 part 内的字节偏移，分别包含和不包含边界。`segment.text` 是回答片段，不是网页摘录。没有候选项时检查 `promptFeedback.blockReason`；有候选项时区分 `finishReason`（例如 `SAFETY`、`RECITATION`、`MAX_TOKENS`）和是否存在可用来源。`urlContextMetadata.urlMetadata[]` 按 `retrievedUrl` 读取 `urlRetrievalStatus`：两份 REST 参考均列出 `URL_RETRIEVAL_STATUS_{UNSPECIFIED,SUCCESS,ERROR}`，Developer API 另列 `URL_RETRIEVAL_STATUS_PAYWALL`、`URL_RETRIEVAL_STATUS_UNSAFE`。缺失、未知或非 `SUCCESS` 的状态不得当作检索成功；`SUCCESS` 只确认模型取到了内容，没有正文响应字段。[Gemini REST](https://ai.google.dev/api/generate-content) · [Vertex REST](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/reference/rest/v1/GenerateContentResponse)
- **OpenAI、Azure OpenAI 与 xAI。** Responses 按 `output[].type` 和 `content[].type` 解析，不假设第一个条目是回答。OpenAI/Azure 的成功样例是 `web_search_call.status="completed"`、`action.type="search"`；缺调用项或没有可用来源时，不能从模型正文补造结果。OpenAI 指南描述 `action.queries` 可能缺失，样例使用单数 `action.query`；解析不应依赖任一字段存在。`include:["web_search_call.action.sources"]` 获取 `action.sources`；Azure 明确每项只有 `type` 和 `url`，标题从 `message` 内 `output_text.annotations[]` 的 `url_citation` 读取。Azure 的推理模型可以用 `include:["web_search_call.results"]` 请求搜索摘录，但 `open_page`、`find_in_page` 不会由此交付结果，且 `external_web_access` 始终按 `false` 处理。xAI 从同一注解路径读取 `url`，文本引用的 `title` 是编号，`start_index` / `end_index` 按字符且尾端不包含；`include:["no_inline_citations"]` 仍可能返回来源注解，但没有正文位置。xAI Python SDK 的 `response.citations` 属于 SDK 路径，不应当作 Responses JSON 的必有字段。上述浏览动作、引用和摘录均不能作为指定 URL 正文。[OpenAI 搜索](https://developers.openai.com/api/docs/guides/tools-web-search) · [Azure 搜索](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/web-search) · [xAI 引用](https://docs.x.ai/developers/tools/citations)
- **Ali。** DashScope 的 `output.search_info.search_results[]` 样例以 `index`、`title`、`url` 提供来源；Responses 可能返回多个 `web_search_call`，应遍历所有 `action.sources`。官方简化 JSON 把来源显示为链接列表占位，SDK 例子读取 `source.url`；不能据此确定字符串和对象都是受支持的线上形状。兼容 Chat Completions 没有结构化来源。`usage.plugins.search.count` / `usage.x_tools.search.count` 只表示检测到搜索意图，即使限流或零结果也可能非零。搜索结果触发内容审查时文档列出 HTTP `400` / `DataInspectionFailed`。提取的流式示例读取 `response.output_item.done` 中 `item.type="web_extractor_call"` 的 `item.goal`、`item.output`；`response.completed` 和 `tool_usage.web_extractor.num_requests` 不证明指定 URL 的正文已交付。Anthropic 兼容协议记录 `server_tool_use`、`web_fetch_tool_result`，单挂 `web_fetch` 会返回 `InvalidParameter`；文档没有定义该结果块内的正文路径，也没有给出 Responses `item.output` 的正文、URL、部分成功和错误结构，需重放样本后再选择 Fetch 解析器。[Ali 搜索](https://www.alibabacloud.com/help/en/model-studio/web-search) · [Ali 网页提取](https://www.alibabacloud.com/help/en/model-studio/web-extractor)
- **AdvancedCustom → Exa。** 只有明确配置为 Exa 的上游才适用此契约。`POST https://api.exa.ai/search` 传 `query`，可传 `numResults` 和 `contents.highlights:true`；读取 `results[]` 的 `url`、`title`、可选 `publishedDate` 与 `highlights[]`。`POST https://api.exa.ai/contents` 传 `urls:[目标 URL]` 和 `text:true`，从 `results[].text` 读取提取正文，不用 `summary` 或 `highlights` 补正文。两条路径均支持 `x-api-key` 或 Bearer。`/contents` 即使 HTTP `200` 也要按 `statuses[].id`（请求 URL 或文档 ID）独立检查 `status:"success"|"error"`；可选 `source` 是 `cached` 或 `crawled`，失败详情是 `error.tag` 和可空的 `error.httpStatusCode`，后者不得与 Exa 外层 HTTP 状态混淆。不要按数组位置绑定 `statuses[]` 与 `results[]`；如果没有可归属给请求目标的非空 `text`，就没有可交付正文。外层规范另列 `400/401/402/403/429/500/503`；普通错误体有 `requestId`、`error`、`tag`，未知 tag 按外层状态处理。`402` 可能表示有 key 但余额或预算不足，不能当作目标网页状态。[Exa Search](https://exa.ai/docs/reference/search) · [Exa Contents](https://exa.ai/docs/reference/get-contents) · [Exa OpenAPI](https://exa.ai/docs/exa-spec.yaml)
- **AWS Bedrock Mantle。** 从 `output[]` 的 `message` 项内读取 `content[]` 中 `output_text.annotations[]` 的 `url_citation`（`url`、`title`、`start_index`、`end_index`）；SSE 对应 `response.output_text.annotation.added`。`external_web_access` 请求默认值为 `true`；缺 `bedrock-websearch:ExternalWebAccess` 时，Fetch 授权会在读取缓存之前失败，外层仍可能 HTTP `200` 并带搜索引用。显式设为 `false` 才可在有 `bedrock-websearch:InvokeFetch` 权限时走仅缓存路径。AWS 将 `fetchedSources` 记录在启用数据事件日志的 CloudTrail 中；它不是推理响应字段。不要从引用、回答或 HTTP `200` 推断 Fetch 成功，该接口也没有面向调用方的正文契约。Mantle 的字段和权限不适用于现有 Bedrock Runtime Claude `InvokeModel` 渠道。[AWS Web Search](https://docs.aws.amazon.com/bedrock/latest/userguide/web-search.html) · [CloudTrail 监控](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-web-search.html)

## 接入判断与验证边界

- **合成回放用例已编写，待运行：** 智谱 Reader Fetch、Claude Messages Search/Fetch、Gemini Developer/Vertex Search、OpenAI/Azure/xAI/Ali Responses Search；已有智谱及百度 REST Search 用例。源文件见 [`hosted_tools_test.go`](../service/websearch/hosted_tools_test.go) 和 [`rest_search_test.go`](../service/websearch/rest_search_test.go)。依赖推理模型的工具操作需要在渠道显式配置模型映射；智谱 Reader 不需要推理模型。新增操作须完成能力目录登记并通过统一选渠后才可使用。无效的正文 URL、搜索空响应和失败的工具结果不会从模型回答补齐。
- **真实账号验证：** 本轮未调用真实账号，尚须验证部署、模型、额度与权限。新托管请求暂不写共享缓存，避免缓存生成正文、加密字段或工具错误；接入规范化后缓存时需验证缓存失效与保护请求隔离。
- **当前契约不向调用方交付网页正文：** Gemini/Vertex URL Context、OpenAI/Azure/xAI Responses 的浏览动作、AWS Mantle 搜索引用及百度搜索片段，不登记 Fetch。
- **尚缺接入证据或配置：** Ali 网页提取的 URL、正文与错误回放；AWS Mantle 和 Claude Platform on AWS 各自的路由与鉴权证据；智谱国际站和 Coding Plan 的凭据验证。AdvancedCustom 的逐操作 Exa 验证已接入，真实账号验收见上节。

凭据验证应分别采集一次明确命中及一次空结果或工具错误；对于 Fetch，另需使用正文已知的公开页面确认 URL 和实际正文，覆盖目标不可达以及 HTTP 成功但工具失败的情形。重放前移除凭据，保留响应状态、工具调用和结果块以及解析需要的字段。文档结论与实际渠道资格在这些样本就绪前保持分开。
