# Image Limit Rules

Per-model and per-channel image ceiling. Code: `relaykit/dto/channel_settings.go` (`MaxImagesPerRequest`, `MaxImagesPerModel`), `relay/common/image_limit.go`, `relay/image_limit.go`, `controller/relay.go`, `pkg/metrics/image_limit.go`.

## Counting images

- `relay/common/image_limit.go` counts how often a request carries an image, not how many distinct ones: the upstream validates the occurrence count of the parts it receives, so a repeat counts again.
- Carriers: OpenAI Chat `image_url`; Responses `input_image` by URL; Claude `image` blocks of system prompt, messages and nested `tool_result` content; Gemini `inlineData`/`fileData` parts of image MIME type, including those a `functionResponse` replays.

## The limit lookup

- HTTP and Responses WebSocket call `RequestPreprocessing.ApplyForAttempt` before sending upstream. It passes the selected channel settings and model mapping from the request context to `CheckRequestImageLimitForModels`; the placeholder channel in `controller/relay.go` has neither. `UpstreamModelNames` lists the requested model, the name its reasoning suffix strips to, and the name the channel `model_mapping` sends it under (chain followed to its end; a self-map stops where it is). First hit in `ChannelSettings.MaxImagesPerModel` supplies the limit, a miss falls back to `ChannelSettings.MaxImagesPerRequest`.
- A `model_mapping` cycle is refused locally with `400 invalid_request` and `model_mapping_contains_cycle`; `helper.ModelMappedHelper` rejects the same mapping later with `channel:model_mapped_error`.
- Exactly that many images still goes out; the first past it is refused in the retry loop before the handler runs. Zero or missing leaves the channel unlimited; `ValidateHTTPTransport` rejects a negative value at save time. A Mistral Studio key rejects the ninth image on the weaker models and the twenty-first on the stronger ones, so channels carry a per-model ceiling and keep 20 channel-wide as fallback.

## The local refusal

- HTTP 400, `error.code` `context_length_exceeded`, `ErrOptionWithSkipRetry`; the channel is not disabled. `imageLimitMessage` assembles the ceiling sentence, `imageLimitRetryHint` and `imageLimitContextOverflowHint`: `Total number of images (<n>) exceeds the maximum allowed of <limit>. Request a smaller batch of images or compact the conversation and retry. Request exceeds the context length limit; compact the conversation before retrying it.`
- The text, not the code, makes clients compact: Kimi Code 2.4.1 on Chat Completions reads a 400 as a context overflow only on a `/context[ _-]?length/i` match. A code-only reply against a mock upstream failed with `provider.api_error: 400 ...` and exit 1; the same body with the phrase compacted, retried, exited 0.

## Recognising the upstream wording

- `TranslateUpstreamImageLimitError` matches the message against `upstreamImageLimitWordings`, a commented table of the two wordings measured on the upstreams, and rewrites a matching 400 into the same 400 with `error.code` `context_length_exceeded`, clearing the skip-retry flag and leaving a channel without a fault enabled.
- `api.mistral.ai` counts a whole request: `images … exceeds? … maximum allowed`, case-insensitive, verb in either number (`exceeds`, `exceed`), count not part of the match, a number required after `maximum allowed`.
- Command Code, the `deepseek-v4.1-flash-dedicated` model behind channels 3 and 4, counts images after the last assistant message: `This turn adds <m> images (the images after the last assistant message); deepseek-v4.1-flash-dedicated takes at most <n> new images per turn. Images earlier in the conversation do not count.`, matched by `takes at most <n> new images per turn`. Its ceiling is per turn, so a sentence without `per turn` is left alone.
- The rebuilt message uses `err.MaskSensitiveError()`, the masked text the envelope would have written, so an echoed key stays masked, and carries the same `imageLimitContextOverflowHint`. Unchanged: an error new-api raised itself, a 400 of another kind, another status, a channel fault.
- The retry loop calls the translation after `ObserveUpstreamAttempt` and before `DecideRelayRetry`/`processChannelError`, settling the retry decision and the final reply. An adaptor writing a non-200 body and returning no error counts the attempt as a success; `GeminiHelper` returns the error instead, its non-200 answer becoming `service.RelayErrorHandler` before `adaptor.DoResponse` runs, so a non-streaming Gemini refusal reaches the translation.

## The Claude envelope path

- An upstream answering a Claude request with the Messages API error envelope is read by the Claude handler, not `service.RelayErrorHandler`. `claudeEnvelopeStatusCode` raises that envelope with the upstream's status, so the measured 400 reaches the translation instead of the former 500; a 2xx answer keeps the 500, a non-200 answer of another kind still goes through `service.RelayErrorHandler`.
- A streaming request refused with a non-200 is not the committed-stream case: `StartRelayStreamKeepAlive` runs only for a 2xx answer, so headers are uncommitted and the client reads the refusal with the upstream's status. `service.RelayErrorHandler` would read an OpenAI-shaped error object and answer `bad_response_status_code` for a Claude envelope written as `event: error` plus a `data:` line.
- `relay/claude_handler.go`'s `channelErrorEnvelopeRefusal` therefore reads a non-200 answer of a Claude channel first: drains the body and puts it back, keeps the payload of the last `data:` line for an event stream and the body itself otherwise, and raises the envelope with the upstream's status only when `error.type` is non-empty and `error.message` names the image ceiling (`NamesUpstreamImageLimit`).
- Every other answer goes back to `service.RelayErrorHandler` untouched, keeping its code, source, retry and disable decisions: `RelayErrorHandler` unwraps any `error` object as an OpenAI error, and raising a rate limit or admission error as the envelope would turn a reply new-api skips into one it retries and let `service.ShouldDisableChannel` act on the raised form. A channel fault needs no guard: `service.RelayErrorSource` answers `"channel"` for any `channel:*` code before looking at the message.
- `ClaudeHelper` uses it for every `/v1/messages` request, `ResponsesHelper` for a `/v1/responses` request on a Claude channel the adaptor converts into the Messages API; both paths and both answer shapes reach the translation, written as `writeRelayStreamError` writes it for the client's route (no new frame format).
- The envelope status is kept inside `relay/channel/claude/relay-claude.go` on all three paths that read one: `HandleClaudeResponseData` for a non-streaming reply, `HandleStreamResponseData`, called by the stream scanner with the response it reads, and `ClaudeResponsesStreamHandler` in `relay_responses.go` for the Claude-to-Responses stream. The AWS adaptor invokes a model stream without an HTTP answer, so it keeps the 500.

## The Gemini stream look-ahead

- A streaming Gemini request starts its keepalive on the upstream's 2xx, so the event stream is committed before the first body byte and a refusal inside it cannot carry a status code of its own.
- `GeminiTextGenerationStreamHandler` reads one event ahead, and only one: `pendingStreamRefusal` takes the first complete event of a 200 stream, spelling every line into a buffer until the blank line that closes the event, and leaves the reader it filled at the head of `resp.Body` through `restoreStreamBody`; an upstream delivering events one at a time is held back by one event, and no byte read ahead is lost.
- When that event names the image ceiling (`errorObjectNamesImageCeiling`), the handler returns the error `upstreamImageLimitRefusal` builds from it without writing. The controller's defer finds headers committed and writes that one error event with `writeRelayStreamError`: the client reads HTTP 200, `text/event-stream`, the chunks delivered before the refusal, then `data: {"error":{…,"code":"context_length_exceeded"}}` and `data: [DONE]`. Caught before any byte went out, headers stay uncommitted and the client reads a plain 400 with the same code and wording.
- An event after the first that names the ceiling is caught by the stream callback, which returns the same error and stops, so the chunk before it still reaches the client and only one error event ends the stream. An event the wording does not match streams as before.
- `upstreamImageLimitRefusal` does not translate the event: it keeps the sentence an envelope carries, and the retry loop translates, reaching every error a handler returns twice (adaptor, then `controller/relay.go`), so `TranslateUpstreamImageLimitError` returns a refusal already ending with `imageLimitContextOverflowHint` unchanged. The guard reads the closing hint only: a translated refusal carries `imageLimitErrorCode`, but so may one the upstream wrote itself (`3051` carries it in the measured reply).
- The ceiling wording lives in this package, which imports the adaptors, so gemini cannot read it: `relay/image_limit.go`'s `init` hands `NamesUpstreamImageLimit` and `upstreamImageLimitRefusal` to `gemini.SetStreamRefusalNamesCeiling` and `gemini.SetStreamRefusalError`.

## The OpenAI and Claude stream hooks

- The OpenAI, Claude and OAI-format Gemini chat handlers return the error directly (`ResetStatusCode` only remaps with a non-empty `status_code_mapping`), so those formats reach the translation whether or not they stream. A refusal inside their stream uses the same registration: the `init` above hands `translateClaudeImageCeiling` to `claude.SetImageCeilingRefusal` and `translateOpenAIImageCeiling` to `openai.SetImageCeilingRefusal`; each handler asks its hook about an event, so a refusal after the 200 headers are committed is returned to the controller, not forwarded as content, and written once with `writeRelayStreamError` after the chunks already sent.
- The OpenAI handler reads the refusal before holding back the chunk it would have forwarded, so every chunk is already written, in every format; the stream ends on the relay's error event with no closing frame, as the Gemini look-ahead ends one. The Claude handler asks its hook before reading an event as a Claude response, because another format's channel ends its stream with an error object conversion cannot hold.
- The frame the client reads is the one its route asked for: a Claude route writes `event: error` with `data: {"type":"error","error":{"type":"context_length_exceeded","message":…}}` and nothing after it; an OpenAI or Gemini route writes `data: {"error":{…,"code":"context_length_exceeded"}}` then `data: [DONE]`.
- `upstreamImageLimitRefusal` keeps the whole event unless its error object's sentence names the ceiling. An event names its error object under `error` or as the event itself with `object` set to `error`; an event whose `error` is not an object never counts, even when another field carries the ceiling wording.

## Tests and metrics

- `relay/image_limit_test.go`: recognition and rewrite of both wordings, the plural verb, the channel fault, the masked `https://user:KEY@host` message against `ToOpenAIError`, the per-turn body read through `service.RelayErrorHandler`, and counter-cases left unchanged (`This turn adds <m> images` without a ceiling, `takes at most <n> images` without `per turn`, another status, a reply new-api raised itself). `TestImageLimitRefusalReadsAsAContextOverflow` requires the local and translated refusal to match `/context[ _-]?length/i` while keeping status, code and skip-retry flag; `TestPreviousImageLimitWordingDoesNotReadAsAContextOverflow` shows it does not match. Same file: the translations themselves (`TestStreamImageCeilingReadsAsAContextOverflow`, `TestStreamImageCeilingKeepsTheEnvelopeOfTheClient`, `TestStreamCeilingReadsAnErrorObjectAtTheTopLevel`, `TestStreamErrorOfAnotherKindIsNotTranslated`, `TestStreamSentenceIsReadFromTheErrorObject`) and `restoreImageCeilingHooks`, which restores the real hooks the relay import's `init` registers.
- `controller/relay_image_limit_test.go` drives a real httptest upstream returning 400 through the loop: a Claude `error` envelope of the Messages API on the non-streaming and pre-stream 400 path (`TestRelayTranslatesAClaudeEnvelopeImageCeiling`), the same envelope on `/v1/responses` (`TestRelayTranslatesAClaudeEnvelopeImageCeilingForResponses`), the Command Code per-turn body, and native Gemini `:generateContent` plus a `:streamGenerateContent?alt=sse` whose stream opens with the refusal and one carrying an event before it (`TestRelayTranslatesAnUpstreamImageCeilingForGemini`); asserts one upstream attempt, no retry event, `ShouldDisableChannel` false.
- Counter-cases there: an envelope of another kind, settled as a non-retried 400 that disables no channel, whose client-visible `error.type` is the string `"<nil>"`, because `service.RelayErrorHandler` decodes it into a `types.OpenAIError` whose `Code` is empty and `NewAPIError.ToClaudeError` writes that field with `%v` (`TestRelayKeepsAClaudeEnvelopeErrorOfAnotherKind`); an OpenAI-shaped 400 that is no envelope (`TestRelayKeepsAClaudeNonEnvelopeStreamError`).
- `TestRelayKeepsANonImageGeminiStreamError`: a stream error of another kind keeps its code. `TestRelayKeepsAGeminiStreamThatOpensWithAChunk`: a stream the look-ahead does not refuse reaches the client event by event. `TestRelayStreamsGeminiEventsAsTheyArrive`: the upstream is held between first and second event and the first must reach the client within two seconds, which a one-event look-ahead satisfies and a run-to-the-end one does not. `TestRelayKeepsTheGeminiEventBeforeAnImageCeiling`: the chunk before the refusal reaches the client.
- `streamErrorEnvelope` reads the last `data:` frame, which the last case and `assertImageOverflowWording` require to carry `context_length_exceeded` and match `/context[ _-]?length/i`. `requireImageCeilingMessageToldOnce` adds to the three Gemini paths that each hint is told once and the upstream envelope is absent.
- `streamGenerateContent refused before the first event` is not a look-ahead case: such a refusal is caught by the stream callback too, even with nothing read ahead, so it checks the reply, not that the look-ahead ran; `service.RelayErrorHandler` cannot answer for it, running only on a non-200 while this upstream answers 200. The look-ahead is covered by the refusal after a chunk, in `streamGenerateContent refused after an event` and `TestRelayKeepsTheGeminiEventBeforeAnImageCeiling`: removing the stream callback's `streamRefusalErrorFor` there leaves the client with a 200, the chunk and no error event; `TestRelayStreamsGeminiEventsAsTheyArrive` covers the look-ahead reading one event and no more.
- `relay/channel/claude/relay_claude_stream_error_test.go` covers the status the Claude handlers raise an envelope with (`TestClaudeStreamHandlerKeepsTheStatusOfAnErrorEnvelope`, `TestClaudeEnvelopeKeepsTheUpstreamStatusCode` in `relay_claude_test.go`) and, with `relay/channel/openai/relay_openai_stream_error_test.go`, the two handlers with a stubbed hook: two chunks then a ceiling reaches the client as both chunks and no content chunk of the refusal; an error chunk of another kind streams as the upstream wrote it; a handler with an unregistered hook streams the event as before.
- `controller/relay_image_limit_test.go` drives the same committed stream through `Relay` for a Claude, OpenAI and Gemini client (`TestRelayKeepsTheChunksBeforeAStreamRefusalForClaude`, `…ForOpenAI`, `…ForGemini`), two chunks before the refusal, requiring both chunks, then the refusal in the route's format, and one upstream attempt.
- `newapi_image_limit_rejections_total{channel,model}` counts refusals made before the upstream is called, labelled with the channel name when one is resolved and the model the client asked for; a translated refusal is not counted.
