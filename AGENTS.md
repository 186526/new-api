
## Fork Maintenance

This tree is a self-hosted fork of `QuantumNous/new-api` (remote `upstream`). It is maintained independently: upstream is a read-only reference, and only selected features are brought back.

### Upstream

- Do not merge `upstream/main` on a schedule. `master` is the deployed line and carries its own features.
- To bring an upstream feature in, cherry-pick the single commit and resolve conflicts against this tree. Do not merge an upstream branch wholesale.
- Keep the diff against upstream limited to the entries in the table below so later picks stay small.
- Verify a pick with `go build ./...` and the tests of the touched packages.
- The deployed commit is tagged `deploy-<YYYYMMDD>`; `git log deploy-<YYYYMMDD>..master` lists what is built but not yet released.

### Remotes

- The checkout on this workstation is often on a detached HEAD while the local `master` ref lies behind `origin/master`. `git push origin master` then fails with a non-fast-forward even though the new commits are ancestors of `origin/master` plus your own; push the commit you are on instead: `git push origin HEAD:master`. Check `git status -sb` for `HEAD（非分支）` before pushing.
- `origin` is `git@github.com:186526/new-api.git`. The deployment repository `https://git.186526.xyz/186526/kubernetes.git` is the parent tree's remote and holds `deploys/` and `monitoring/`; it does not carry `source/`. Push the fork to `git.186526.xyz` over HTTPS when GitHub is unreachable.
- The parent repository tracks `source/` as a gitlink: `git ls-files -s new-api/source` in `kubernetes/` shows mode 160000 and the commit `source/` is checked out at. Customize here and bump the gitlink to the new `master` commit of this fork whenever a parent change depends on the fork code. The recorded commit must be reachable from the fork remote (`origin`, `git.186526.xyz`), because a fresh clone fetches only what the remote has. Bumping the gitlink is a separate step: a parent commit that did not bump it still describes the previous fork commit, and the image tags in `deploys/` name the `sha-<commit>` CI built for that commit.

### Release

- Every image is built by CI. Do not build images locally, and do not build a binary or a frontend bundle on the workstation to hand-assemble an image: `.github/workflows/master-image.yml` runs on every push to `master` and publishes `ghcr.io/186526/new-api:sha-<commit>` from the `backend` target (built with `-tags no_web_assets`, so the binary carries no dashboard files) and `ghcr.io/186526/new-api:sha-<commit>-web` from the `web` target (nginx plus `web/dist`).
- Before pushing, run the checks CI runs: `go build ./...` and the tests of the touched packages in `source/`, then `bun install --frozen-lockfile`, `bun check -b` and `bun run lint` in `source/web/`. A red check belongs in the commit that fixes it, not in a follow-up push.
- The CI test step is `make test`, which runs `go test` without `-race` on the root, `relaykit` and `tokenkit` modules (`.github/workflows/ci.yml`, the `Test root, relaykit, and tokenkit modules` step). The root step is `GOWORK=off go test ./...`, and `./...` lists package main itself, so `main_test.go` runs there; the earlier form fed `go test` the output of `go list -e ./...` with `go list -m`'s output removed by `grep -vxF`, and because `go list -m` answers the bare module path `github.com/QuantumNous/new-api` while `go list -e ./...` lists that same string as package main, the filter dropped the root package and `make test` passed while `main_test.go` never ran. `./...` does not reach `relaykit` or `tokenkit` because each has its own `go.mod`, so those two keep their own `cd relaykit`/`cd tokenkit` steps. The root step needs `web/dist` because package main embeds it: CI creates `web/dist/index.html` before `make test`, and a local run without a dashboard build can pass `-tags no_web_assets` instead. The race detector is not a gate, so a package that only races under `-race` stays green in CI; run `go test -race -count=1 ./<package>/` yourself after touching a package's test helpers. Tests that pass `-race` must keep passing it; a failure this section describes comes from test helpers, so confirm it is not a product race before calling it a test problem. `relay/channel/gemini` is such a package: its `main_test.go` `TestMain` sets `gin.SetMode(gin.TestMode)` and `constant.StreamingTimeout` once, and no test in the package writes either global. The two globals raced for different reasons. gin keeps its mode in a package variable that parallel sibling tests each overwrote through `gin.SetMode`. `constant.StreamingTimeout` was written by serial tests that set it to `300` and restored the value in `t.Cleanup`; the restored value raced with the read a parallel test made in `relay/helper/stream_scanner.go`.
- The node pulls from GHCR directly, so an image never has to be copied onto it. After CI publishes an image, pull both tags on the node with `k3s ctr -n k8s.io images pull --platform linux/amd64 ghcr.io/186526/new-api:sha-<commit>` and `k3s ctr -n k8s.io images pull --platform linux/amd64 ghcr.io/186526/new-api:sha-<commit>-web`, then point `deploys/30-new-api.yaml` at the `sha-<commit>` tag and `deploys/25-new-api-web.yaml` at `sha-<commit>-web`. A backend-only change does not need a new web image. Measured on 2026-11-21 for `sha-fc9dfe5d4c31711addf512578e0bcd8fbc54e785`: the pull reported `Completed pull ... total: 23.0 M (5.9 MiB/s)` and took 3.9 seconds.
- Do not hand-assemble an image archive and import it on the node with `k3s ctr -n k8s.io images import`: such archives fail there, typically with `ctr: unexpected EOF`, and a manifest that names a blob the node's content store lacks fails earlier with `content digest ... not found`. A `pull` reads the base layers from the registry and fails neither way.
- Keep the previous image tag on the node; rolling back means re-applying the previous tag. `imagePullPolicy: IfNotPresent`, which all three Deployments set, does not block a pull of a tag the node does not have: it only tells kubelet to skip the registry when the tag is already in the node's image store, and lets kubelet pull it when it is not. Roll back by pulling the previous tag on the node first if `crictl images` no longer lists it; otherwise the Deployment stalls with a failed pull for that tag.
- After a release, remove the images the node no longer runs: `crictl images` on the node, then `crictl rmi` for every tag that is neither the current one nor the one kept for rollback, plus every `<none>` entry. Removing by ID also removes every other tag that shares the ID, so when a tag to keep shares its ID, remove the unwanted tags by name (`crictl rmi <image>:<tag>`) and leave the ID alone.

A streaming Gemini request starts its keepalive with the upstream's 2xx, so its event stream is committed before the first body byte and a refusal that arrives inside the stream cannot carry a status code of its own. `GeminiTextGenerationStreamHandler` therefore reads one event ahead, and only one: `pendingStreamRefusal` takes the first complete event of a 200 stream, spelling every line into a buffer until the blank line that closes the event and leaving the reader it filled at the head of `resp.Body` through `restoreStreamBody`, so an upstream that delivers its events one at a time is held back by one event and never by the rest of the stream, and no byte read ahead is lost. The refusal the look-ahead catches before any byte went out is the same error, so it leaves the handler with the headers uncommitted and the client reads a plain 400 with the same code and wording. An event after the first one that names the ceiling is caught by the stream callback, which returns the same error and stops there, so the chunk before it still reaches the client and only one error event ends the stream. An event the wording does not match is streamed as before. `upstreamImageLimitRefusal` does not translate the event itself: it keeps the sentence an envelope carries and leaves the translation to the retry loop, which reaches every error a handler returns twice — once from the adaptor and once from `controller/relay.go` — so `TranslateUpstreamImageLimitError` returns a refusal that already ends with `imageLimitContextOverflowHint` unchanged. A token ledger whose signature is genuine but whose window has closed still answers from the row plus the accumulator's owed delta on both sides; `expireSignedTokenLedger` re-signs a past expiry to produce that state. One token-side difference matters for the hash that has to come back after Redis loses it: `cacheInitToken` fills a fresh hash's `UsedQuota` with the counter the seed signs (`args.seed.used`, which is the snapshot raised by the delta the accumulator still owes it), not the snapshot's own value, because filling the row's value first made the seed decline and published a hash with no ledger, which the reservation refused only until the hash's own TTL expired, after which `cacheInitToken` seeded the ledger from the flushed row |
