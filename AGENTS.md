
## Fork Maintenance

This tree is a self-hosted fork of `QuantumNous/new-api` (remote `upstream`). It is maintained independently: upstream is a read-only reference, and only selected features are brought back.

### Upstream

- Do not merge `upstream/main` on a schedule. `master` is the deployed line and carries its own features.
- To bring an upstream feature in, cherry-pick the single commit and resolve conflicts against this tree. Do not merge an upstream branch wholesale.
- Keep the diff against upstream limited to the entries in the table below so later picks stay small.
- Verify a pick with `go build ./...` and the tests of the touched packages.
- The deployed commit is tagged `deploy-<YYYYMMDD>`; `git log deploy-<YYYYMMDD>..master` lists what is built but not yet released.

### Remotes

- `origin` is `git@github.com:186526/new-api.git`. The deployment repository `https://git.186526.xyz/186526/kubernetes.git` is the parent tree's remote and holds `deploys/` and `monitoring/`; it does not carry `source/`. Push the fork to `git.186526.xyz` over HTTPS when GitHub is unreachable.
- The parent repository keeps `source/` untracked. Never `git add source/` from the parent tree.

### Release

- Every image is built by CI. Do not build images locally, and do not build a binary or a frontend bundle on the workstation to hand-assemble an image: `.github/workflows/master-image.yml` runs on every push to `master` and publishes `ghcr.io/186526/new-api:sha-<commit>` from the `backend` target (built with `-tags no_web_assets`, so the binary carries no dashboard files) and `ghcr.io/186526/new-api:sha-<commit>-web` from the `web` target (nginx plus `web/dist`).
- Before pushing, run the checks CI runs: `go build ./...` and the tests of the touched packages in `source/`, then `bun install --frozen-lockfile`, `bun check -b` and `bun run lint` in `source/web/`. A red check belongs in the commit that fixes it, not in a follow-up push.
- The node cannot pull from GHCR. After CI publishes an image, copy it onto the node and import it with `k3s ctr -n k8s.io images import`, then point `deploys/30-new-api.yaml` at the `sha-<commit>` tag and `deploys/25-new-api-web.yaml` at `sha-<commit>-web`. A backend-only change does not need a new web image.
- Keep the previous image tag on the node; rolling back means re-applying the previous tag. The deployment uses `imagePullPolicy: IfNotPresent`, so an imported tag is never pulled again.
- When the link to the node is slow, do not stream the whole archive: every image differs from its base in one layer, so export the OCI image with `podman save --format oci-archive`, keep `index.json`, `oci-layout`, the manifest, the config and the last layer blob, then import that 40-45 MB archive with `k3s ctr -n k8s.io images import --no-unpack -`. The importer resolves the base layers from the content store, and the 1.4 GB full transfer that used to take 20 minutes finishes in under a minute.
- The last layer is not always the application layer. The backend image ends with the binary copy, then the `COPY LICENSE NOTICE THIRD-PARTY-LICENSES.md /licenses/` layer, so a slim archive must also carry that layer; dropping it makes the pod fail with `content digest ... not found` at container creation. Check `history` in the image config against the layer list before trimming.
- After a release, remove the images the node no longer runs: `crictl images` on the node, then `crictl rmi <id>` for every tag that is neither the current one nor the one kept for rollback, plus every `<none>` entry.
